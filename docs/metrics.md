# Customer metrics

The console **Metrics** sidebar entry opens `/admin/metrics`. Only active administrators can see it or call its reports. Every report passes the existing backend administrator middleware, including upstream profile verification with a maximum thirty-second authorization cache. Signed-out callers receive 401, customers and disabled/revoked administrators receive 403, and a failed administrator verification returns 503. The browser clears Metrics data when authorization fails or the account changes.

## Definitions

- Metrics opens on **Usage overview → Today**. The three main views are Usage overview, Customers, and Activity. Usage overview shows one of Today/All time at a time; Customers and Activity each keep independent report dates, pagination, and refresh generations. Table filters affect only customer rankings. Activity source and chart measure affect only Activity. Choices persist while switching views during the visit, and only the active view fetches or refreshes reports.
- Usage overview separates **Recorded usage** (actual totals and timeline), **Active-hour averages** (finished hours containing requests), **Overall averages · Includes idle time** (smaller, visible calculated rates), and **Busiest actual periods** (completed five-hour windows). Separate calculation disclosures show the included totals flowing through active hours to one/five-active-hour rates, or elapsed time to overall hourly/five-hour/seven-day rates. Summary currency uses two decimals, positive sub-cent values show `<$0.01`, and exact amounts are available on focus/hover/tap. Chart data has an expandable accessible table; console chart details show only observed customer activity.
- The population is the current, non-deleted customer directory (`role=user`), including disabled accounts. Administrators and deleted accounts are excluded. Total users is the current directory count, independent of the reporting dates.
- The reporting range defaults to the last 28 calendar days, including today. Presets for 7, 28 and 90 days, custom dates, and **All time** are available. Custom ranges accept at most 397 inclusive calendar dates; All time resolves all retained history on the backend and may exceed that date limit. Selecting a preset or applying custom dates exits All time. Weeks begin Monday.
- API activity counts customers with recorded requests, including zero-cost requests. Billed spend comes from `actual_cost`, never standard/provider cost. An hourly/day/week distinct-user count is computed independently, not summed from children.
- Console activity counts server-verified, active customers observed on visible console pages, including Playground. Multiple tabs, browsers, and devices for the same account count once per reporting hour. Hidden tabs, anonymous visits, public website traffic, administrators, and known bots do not count. Collection is best effort, not an audit log of successful logins or continuous online presence.
- DAU cards report the last date in the selected range, printed on the card. A dash indicates unavailable observations/history, rather than a measured zero.
- Rankings use the mean of request and billed-spend midrank percentiles among customers with consumption. Top/bottom cohort sizes are `ceil(consumers * 0.2)`; boundary ties remain together. If boundaries overlap, tied customers remain Regular. Customers with no recorded consumption are separate. Small populations or ties can make cohorts larger than 20% or leave no heavy/light cohort.
- **Active-hour averages** apply to Today and All time. An active hour is one fully covered, completed reporting-timezone hour with combined customer requests greater than zero. Multiple customers count as one shared hour, zero-cost requests qualify, and spend-only hours do not qualify. Sum requests and exact billed spend from these same active buckets, divide by their count, and scale directly by 1 or 5. Exclude partial first/current hours from both numerator and denominator; recorded totals still include their usage. These rates can be available after one active hour, and five active hours need not be consecutive. One request makes an hour active; this does not measure continuous activity or specifically busy hours. For $140/1,400 requests across seven active hours among fourteen completed hours, active rates are $20/200 requests per hour and $100/1,000 per five active hours. The labelled active/idle bar covers only fully covered completed hours; the exclusive cutoff is the end of the latest completed hour, including idle hours. Empty completed history has null active rates, not zero averages. No completed history or ambiguous timezone-clock history is unavailable. There is no active-based 7-day projection.
- **Today** and **All time** are selected inside Usage overview. The following existing calculations appear under **Overall averages · Includes idle time**. Today starts at reporting-timezone midnight and labels its five-hour/seven-day figures as estimates at today's average rate. All time starts at the first verified retained request belonging to the included customer population, excluding earlier administrator/deleted-account requests, and labels its figures as average usage per hour/five hours/seven days. Each rate is calculated directly from original totals divided by elapsed hours and multiplied by 1, 5, or 168; idle and fractional hours count. The 7-day figure is a normalized weekly rate over 168 hours, available even before seven days have elapsed. At 12:30, 125 requests/$12.50 gives hourly 10/$1, five-hour 50/$5, and seven-day 1,680/$168. Customers and Activity report dates do not affect these figures.
- A successful empty-day response shows zero totals and zero rates. At exactly midnight, totals remain defined and rates are null until time has elapsed. Empty all-time history has zero totals, a null start, and null rates. Source failures show local errors rather than fabricated zeros; totals/rates and chart/peaks load independently. All figures use retained usage; deleted records cannot be reconstructed, and All time is available history rather than verified lifetime totals.
- **Busiest 5-hour usage** appears beneath both Today and All time, independently of the reporting selector. Separate cards find the most requests and highest billed spend across all included customers; the winning windows may differ. These are actual combined totals, using exact decimal spend, over five consecutive fully covered, completed hours. Windows advance one hour at a time, include idle hours, exclude partial first/current hours, and resolve ties to the earliest start. Start is inclusive and end is exclusive. Today's windows stay within today; All time can cross midnight, weeks, and fetch chunks. Fewer than five eligible consecutive hours is unavailable; eligible windows with no requests/spend explicitly show no usage/spend. A range containing daylight-saving or other clock-transition dates is unavailable for this measure because upstream civil-hour labels cannot identify repeated or skipped hours precisely.
- Heatmaps average each weekday/hour across completely covered occurrences, including zero-use hours. Peaks use complete hours. Partial first/current hours and unavailable periods are excluded. Expandable tables include available partial periods and label them. Civil repeated hours in daylight-saving timezones share the same labeled bucket, matching upstream trends.
- All time activity details show thirteen weeks per page, with the newest page first and week/day/hour expansion preserved. Timelines, heatmaps, and peaks always cover the complete available history, independently of the detail page. Console All time begins at the later of collection start and its thirteen-month retention cutoff; API history uses upstream retention. Timelines include recorded first/current partial periods, marked visibly, but omit future hours. Covered idle periods plot as zero; known uncovered periods plot as gaps. User counts remain independently deduplicated within each hour/day.
- Customers shows current account counts separately from date-specific active counts and report-period totals. Its classification donut includes Heavy, Regular, Light, and No usage across the entire current customer population for the report dates; searching or filtering the rankings table does not change this chart.

## Sources and limits

The backend provides GET `/portal/v1/admin/metrics/overview`, `/users`, `/activity`, `/averages`, and `/peaks`. The first three accept `startDate`/`endDate` or `range=all-time` without dates, and return the resolved `range` (`mode`, nullable `startDate`, `endDate`). User reports additionally accept `cohort`, `search`, `page`, and `pageSize`. Activity accepts `source=console|api` and `activityPage`; All time responses include `pagination` with page, page size, total pages/weeks, and displayed dates; custom responses use null pagination.

Averages accept `scope=today|all-time` (default today), ignoring report dates. Their response contains `scope`, `reportingDate`, nullable `periodStart` (an ISO timestamp), `elapsedHours`, `totalRequests`, `actualCost`, and nullable `hourly`/`fiveHourly`/`weekly` request/spend rates. Peaks accept the same scope and return `scope`, `reportingDate`, and `fiveHourPeaks`: `status` (`ready`, `insufficient-history`, or `unsupported-timezone`), `eligibleWindows`, and nullable `mostRequests`/`highestSpend` winners. Each winner contains ISO `startAt`/`endAt`, `requests`, and decimal `actualCost`. API activity carries the same summary; console activity uses null. Peaks and API activity also return `activeUsage` with `status` (`ready`, `insufficient-history`, or `unsupported-timezone`), nullable ISO `completedThrough`, `completedHours`, `activeHours`, included `totalRequests`/decimal `actualCost`, and nullable `hourly`/`fiveHourly` request/spend rates. Console activity returns `activeUsage: null`. With no completed hours the counts/totals are zero, cutoff/rates null, and status insufficient-history; completed idle hours produce ready with zero active count/totals and null rates. Unsupported-timezone makes all summary values null. Active summaries use the Peaks snapshot's generation time, scope, timezone, coverage, cache, and refresh. Activity and peaks also contain `usageTrend`: `granularity` (`hour` for a single custom date/Today, `day` for multi-date/All time), and ordered `points` with civil `period`, `users`, `requests`, exact decimal `actualCost`, `covered`, and `partial`. All reports include reporting timezone, coverage, and generation time. `refresh` is a bounded numeric cache generation scoped to the view whose refresh button was pressed.

Customer data is loaded from paginated `admin/users`. The source timezone comes from `settings/public.server_timezone` and must match `SERVER_TIMEZONE` (default `Asia/Kolkata`; equivalent IANA aliases are accepted). Admin usage calls carry the current session's token through the existing refresh wrapper, with the native admin UI header. Credentials, private account notes, keys, and internal pricing settings are never included in the report contracts or cached report values.

API trends use complete `admin/dashboard/users-trend` responses: seven-day hourly chunks for activity and five-hour peaks, a single daily query for today's averages, and calendar-month daily chunks for all-time totals/rankings/averages. Full-history activity folds exact hourly values into 168 heatmap cells, single-hour peaks, five-hour peaks, and one slim timeline point per day, retaining detailed rows for only thirteen weeks. Timeline points are copied from complete civil-day buckets so active users are never summed across hours; chunk arrivals are sorted before returning the full history. Five-hour aggregation keeps four leading/trailing aggregated hours per chunk, including unavailable/partial markers, then joins boundaries in chronological order regardless of fetch completion order. All-time peaks, charts, and active-hour averages reuse the activity snapshot, so concurrent requests share the full scan. Active totals/counts fold each combined hour once, separately from five-hour boundary replay; rates are calculated from full-history totals, never averaged from chunk rates or inferred from daily points. Later activity pages preserve the same global active summary. This adds no upstream scan. Additional API activity pages reuse the global summary and fetch only their detail range. At most two upstream calls run concurrently. The service rejects a 10,001-user trend sentinel, incomplete/mutating directory pagination, duplicate/invalid buckets, directories over 10,000 customers, reports over 250,000 source rows, and scans exceeding 2,000 chunks. First-customer verification allows at most 250 pages of 1,000 events. Capacity or source failures never silently shorten history. Today's averages do not depend on the history lookup; today's peaks use retained-history coverage to exclude incomplete hours. No permanent service credentials or gateway changes are required.

Reports are coalesced and cached for sixty seconds per administrator session; all-time averages and five-hour peaks cache for five minutes. Pending scans stay coalesced, with TTL starting on successful completion. Average and peak caches distinguish scope, timezone, and reporting date. Visible browser reports refresh every minute, except all-time averages and five-hour peaks every five minutes. The day updates at midnight and on visibility/focus changes; yesterday's average/peak responses are suppressed, and peak scans that cross midnight restart for the new date. All time requests have a five-minute client deadline. Upstream responses are limited to 16 MiB and the report cache has a 32 MiB serialized-data budget. The page shows independent source errors and the last successful report when appropriate. Console reports do not depend on API usage-history reads; upstream restrictions and compatibility errors are reported rather than bypassed.

## Storage and release

Production console activity reuses `ANALYTICS_DATABASE_URL` and `ANALYTICS_ENABLED`. Additive analytics migration 2 creates customer/hour memberships and collection-start metadata. Memberships store account ID, reporting day/hour, and first/last observation timestamps; no names, emails, or external database foreign keys. They are committed together with the observation batch, with idempotent upserts. Empty heartbeats do not become raw website events. Memberships retain thirteen calendar months; reads enforce the cutoff even while bounded cleanup is catching up. Development memory storage is bounded and resets with the process.

Release the backend first so migration 2 and the new report endpoints are present, then release the console through the existing console/BFF deployment process. The public Sites deployment is unaffected. Confirm `SERVER_TIMEZONE` agrees with the account service, analytics PostgreSQL is available, and collection is enabled. Console history begins with the new collection and cannot be backfilled from anonymous website facts. API coverage depends on upstream retention. Roll back to prior application images while retaining the additive tables and existing database volumes.

The All time, average, five-hour peak, and active-hour average additions need no further database migration. Release the additive activeUsage backend response before the updated console. The averages response uses `weekly` for the 7-day rate. Rebuild the shared contract and release the backend and console together; a stale console may need reloading after the report contract changes.

Validation includes ranking arithmetic, today's rates independent of historical date filters, midnight rollover during caching and upstream requests, complete pagination, server authorization, activity attribution/deduplication, timezone and retention boundaries, UI rendering and expansion controls, and PostgreSQL migration/upsert/restart checks. Run `npm run test:portal`, `npm run typecheck`, `npm run build:console`, and `npm run build:bff`. Run `npm run test:analytics:postgres` with `TEST_ANALYTICS_DATABASE_URL` pointing to a disposable database; the test creates and drops only its own random schema.
