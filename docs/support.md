# Support tickets

Signed-in customers open **Support** immediately to the right of the console's theme selector. The link includes a chat icon and desktop label; mobile retains the icon. Each ticket has a subject and a conversation, with optional customer image attachments. Administrators use the same header link to open the support inbox, search customers or subjects, and resolve or reopen tickets. Resolved tickets are read-only for customers: they can review their history but cannot reopen the ticket or send new messages or images. Only an administrator can reopen a ticket. The compact inbox puts **New ticket** above the status filters, with a **Support settings** ellipsis beside the filters for sound, desktop alerts, and administrator availability.

The **Open** tab is selected by default. Compact ticket rows show the subject and date, with status, total message count, unread badge, and available actions in the footer. Message previews are omitted. Administrators also see customer identity and the selected ticket's preferred language; customers choose their language in the new-ticket dialog without repeating it in the list. A neutral selection and cyan edge identify the open ticket. Lists follow the selected status, search, and page exactly: resolving a ticket removes it from Open, and reopening removes it from Resolved. Selection does not insert an excluded ticket into the list. The current conversation and draft remain available while filters change; administrators can switch to All or Resolved to find a resolved ticket's Reopen action. Mobile **Back to tickets** returns to the filtered list without clearing the conversation or draft.

The conversation uses a centered reading column up to 760 pixels wide, without repeated page or ticket headers. Each participant sees their own messages on the right and incoming messages on the left; text stays left-aligned inside restrained chat bubbles. Consecutive messages from the same sender within five minutes share a visible sender heading; each message retains its timestamp and applicable receipt, and local calendar days have dividers. The message field and Send button sit side by side, aligned with the thread; multiline messages grow the field to a bounded height, with image controls below. Sending keeps the message field focused and temporarily read-only so the next message can be typed after completion without clicking again. Failed sends retain the draft and caret; responses never pull focus back from another control or conversation.

**New ticket** opens a modal with Subject, Preferred language, Message, and an optional image. English is the default; German, Japanese, Chinese, Korean, French, Spanish, and Vietnamese are also available. This is a per-ticket reply preference, not automatic translation or a change to the English interface. Closing the modal preserves its text, language, and image draft as well as the conversation beneath it. Subject receives initial focus, keyboard focus stays in the dialog, and dismissal is disabled while creating a ticket. A successful submission clears the creation draft and opens the new conversation. The `?new=1` link opens the same modal, including when a `ticket` query parameter is present.

The public footer links to sign-in with Support as the return destination. Customers can access only their own tickets. Customer message metadata shows timestamps without Sent/Seen labels or receipt ticks. Administrators retain Sent/Seen indicators on their own replies; customer responses and events never expose when an administrator read a message. A message is acknowledged after it is displayed in a focused, visible conversation; read acknowledgments pause while the new-ticket dialog covers it.

## Storage and deployment

Support uses the existing BFF, PostgreSQL, and Redis stack. Configure `SUPPORT_DATABASE_URL`, or leave it empty to reuse `PLAYGROUND_DATABASE_URL`, then `ANALYTICS_DATABASE_URL`. Support remains independent of the Playground and analytics feature switches. Production requires `REDIS_URL` for shared live events and availability; development without Redis uses process-local event delivery only. Ticket history always requires PostgreSQL.

The BFF creates separate additive `kr_support_tickets`, `kr_support_messages`, and `kr_support_images` tables under an initialization lock. Existing account, analytics, and Playground records are unchanged. Include these tables in the database's normal backups. Deploy the BFF before the console, together with the updated console CSP permitting `blob:` image previews. No upstream Sub2API changes or additional service are needed. A database outage displays an unavailable state and retains unsent drafts; it never silently substitutes temporary message storage.

Ticket creation accepts `preferredLanguage` (`en`, `de`, `ja`, `zh`, `ko`, `fr`, `es`, or `vi`) in JSON or multipart requests. The value is stored in existing ticket JSONB and included in ticket responses; omitted inputs and legacy tickets default to `en`, without a schema migration. Reusing a creation retry ID with a changed language is a conflict. Customer status changes return 403; new customer replies to resolved tickets are also rejected by the store, including image replies and concurrent writes. Identical retries of previously committed messages remain successful without reopening or changing the ticket. Administrator status changes publish the existing ticket event only on an actual change, without creating a message or changing read/unread counters.

`GET /portal/v1/admin/support/health` is administrator-only and reports configured storage and realtime health. Standard BFF liveness remains independent of support. Logs report delayed delivery without recording message bodies. Retry identifiers make writes idempotent, and committed messages remain successful if publishing a live update temporarily fails. Clients refresh saved state after reconnecting and periodically reconcile while open.

## Availability

Automatic availability is Online after console interaction, Away after five minutes without activity, and Offline after two minutes without a heartbeat. Heartbeats run every 30 seconds. Activity is combined across the administrator's tabs. Manual **Online** stays Online through inactivity, logout, and closed browsers until the administrator chooses another mode. Manual Away still becomes Offline when every heartbeat expires; Offline always overrides activity. Redis remembers the selected mode. Customers can send messages and administrators can receive alerts in every status.

The customer sidebar places availability and **New ticket** side by side below Search. A compact, high-contrast tooltip floats above the availability label with a small pointer and a short hover delay; keyboard focus and tapping show it immediately. It stays within the viewport, escapes sidebar clipping, and closes on Escape or outside interaction. Administrators use **Edit status** in Support settings to save one plain-text message up to 160 characters. Clearing it restores the availability-specific default wording. Availability and status text update live; an unavailable connection shows neutral wording instead of stale Online status. `PATCH /portal/v1/admin/support/presence` accepts `mode`, `statusText`, or both; customer presence responses/events include the text but never the administrator's selected mode.

When connected and Online, the console's Support navigation label is green with a gently pulsing green dot. Away uses a static amber dot and Offline uses gray. A disconnected live stream displays a neutral status instead of claiming support is online. Tooltips and accessible link names include the status; unread badges remain independent. Mobile uses the same status on its Support icon. Reduced-motion preferences disable the pulse.

When support is Away or Offline, the sidebar tooltip adds **Last seen** below its status message, formatted in the customer's local date and time. It reflects the latest genuine administrator activity reported by an active heartbeat, not a background heartbeat or a manually forced Online setting. Redis retains that timestamp without expiry; older installations can use their existing activity record until the next active heartbeat. An unknown timestamp displays **Last seen unavailable**. Online and disconnected states omit the line. Presence HTTP responses and live events include `lastSeenAt`, with `null` when unknown.

## One-time welcome

After five seconds in a visible, focused customer panel, the console calls `POST /portal/v1/support/welcome`. The server creates an open **Welcome to kineticRouter** conversation with a Support message inviting API questions and follows on the configured social channels. All customers, including existing accounts, receive it once; administrators do not. A partial unique PostgreSQL index on welcome ticket owners guarantees one conversation across concurrent tabs, devices, retries, later logins, and resolution. Only the creation winner receives the welcome notification; other tabs refresh their ticket lists without a duplicate sound or toast. Support failures do not block authentication, and the console retries while available.

The dismissible notification offers **Open chat** and does not redirect or take focus. Its sound follows the existing preference and deduplication rules. The welcome remains saved and unread if notification delivery is interrupted. The conversation displays the current configured Telegram, WhatsApp, Instagram, Facebook, and X links with their icons and names. Blank links stay hidden, and a settings outage never restores removed default links. Customers can reply with text or an image; the same resolved-ticket policy applies.

Administrators open **Welcome messages** from their Support sidebar to view `/admin/support/welcome`. Its searchable report shows recipient identity, sent time, first viewed time, first replied time, and a link to the conversation, with 30 entries per page ordered by send time. Unanswered welcomes are excluded from the regular admin inbox; the first customer reply brings the same conversation into that inbox and preserves the welcome report entry.

`GET /portal/v1/admin/support/welcome` serves the administrator-only report. `POST /portal/v1/support/welcome/viewed` acknowledges the caller's welcome only when the actual message is visible in a focused, uncovered conversation. Notification delivery, history requests, read-cursor advancement, and administrator views do not count as viewing. First-view and first-reply timestamps are immutable, private to administrators, and do not change the ticket's status or activity ordering when viewed. Both metadata and the automated message are created atomically; existing ordinary tickets require no backfill. Deploy the additive backend changes before the console.

## Notification sound

The supplied `universfield-message-notification-199577.mp3` is stored unchanged as `apps/console/public/sounds/message-notification.mp3` and is included by Vite in production assets. Its SHA-256 is `7A520887E33C4B594A80ABAE43C972358F693E44B11B0EA15EB9797843545390`.

Sound is on by default for both participants; an explicit mute is saved per account and browser. Normal clicks or keyboard interaction quietly activate browser audio without playing a sample. If the browser blocks a message sound, a compact activation hint appears. Only administrators have **Test sound**, inside **Support settings**. Sound uses the actual MP3, without an additional outgoing-message sound. Multiple eligible tabs coordinate so an incoming message sounds once per browser/account. Optional desktop alerts are independently controlled; their system sound is suppressed so the MP3 remains the notification sound.

A persistent connection covers all console pages and stays active in background tabs and minimized windows. Test on desktop Chrome and Edge with the site unmuted and the device awake. Browsers may suspend or discard tabs; closed browsers, sleeping devices, operating-system restrictions, and suspended tabs cannot guarantee playback. On resume, messages are restored without replaying old notification sounds. Closed-browser push notifications are outside this version.

## Customer images

Customers can attach or paste one JPG, PNG, or WebP image per message, with optional text. A new ticket still requires a subject. Additional images can be sent in later messages. The composer previews the original image, displays its file size, and retains the same bytes for retries. Original draft blobs are stored in IndexedDB per account, tab, and ticket; sending, removal, and logout clear them. Abandoned local image drafts expire after seven days. When browser storage is unavailable, the image remains in memory and the interface explains that it cannot survive a reload. Legacy image drafts from the browser-compression version require reattachment; message text remains saved.

Source files are limited to 10 MiB and 32 megapixels. The browser validates dimensions and uploads the original bytes without canvas encoding, so browser canvas protection cannot replace the attachment with noise. The server uses the existing Sharp dependency to validate one still image, apply its orientation, strip metadata, resize without enlargement to at most 1600 pixels on the longest edge, and save WebP no larger than 512 KiB. Quality and dimension fallbacks keep stored files bounded; originals are not persisted on the server. An 11 MiB multipart request limit applies only to customer create/reply endpoints; ordinary JSON keeps the 128 KiB limit. Deploy the updated BFF before the console so original uploads are accepted. Already-corrupted saved images cannot be reconstructed and require the customer to send the original again.

Image bytes live in a separate PostgreSQL `bytea` table, saved atomically with the message and removed by its foreign-key cascade. Lists, message JSON, and live events carry only metadata and an authenticated image URL. Reading an image requires the owning customer or a current active administrator. Images use private, no-store responses and are never public assets. Identical retries reuse the original message; changing its image or text with the same retry ID is a conflict. Image-only messages contribute to the ticket's message count and produce one normal incoming-message alert.

## Validation

Run `npm test`, `npm run typecheck`, and `npm run build`. Support tests cover authorization, private receipts, idempotent concurrent sends, unread counts, history pagination, automatic presence, event isolation, shutdown/revocation, notification deduplication, and interrupted streams. To exercise real PostgreSQL persistence, set `TEST_SUPPORT_DATABASE_URL` to a disposable local test database before running `npx vitest run test/support-store.test.ts`; tests create and remove isolated schemas.

Browser acceptance checks: create/reply/resolve/reopen with separate customer/admin sessions; confirm only admin sees Seen; resolve under Open and confirm the row disappears, then find it under Resolved and reopen as administrator; confirm selection cannot bypass search or pagination; change availability through Support settings and verify the navigation indicator; preserve a draft after navigation and a failed send; test audio while viewing another console page, another browser tab, and a minimized window; open two console tabs and verify one sound per incoming message; inspect the compact composer and mobile Back navigation in both themes and with reduced motion.

For image and focus regressions, send consecutive replies with Enter and Send while checking focus during delayed and failed requests, and verify that navigation is not interrupted when a request completes. Upload and paste real images with browser canvas exports blocked or corrupted; compare served pixels with the expected content, confirm the stored size and dimensions, and verify original-image drafts across reloads, retry, and the legacy reattachment notice.

The current version supports one administrator workflow and customer image attachments. Guest chat, staff assignment, priorities, typing indicators, arbitrary file attachments, administrator image uploads, email alerts, and Web Push are outside this version.
